# 单次审批接口和实现状态

本分支实现检查与单次审批的关联、待批计划恢复、仅判断模式和持久日志确认。保守历史已接入 Graph 候选事实、有序效果记录和预算耗尽保护，但历史候选尚未贯通风险消费者；本分支不能作为完整的风险消除保护发布，也不能据此重跑正式 RQ2。

## 检查和授权

沿用现有 `check` 消息，不增加第二套检查器。请求的 `intent` 默认为 `propose_for_execution`；`judge_only` 不提交当前命令效果，也不生成可授权的计划。观察序号和请求带入的已有 Shell 状态仍可更新。

| 判断 | 拟执行模式 | 仅判断模式 |
| --- | --- | --- |
| Allow | 立即接受推定效果 | 不接受当前命令效果 |
| NeedApproval | 保存原检查计划并返回回执 | 不保存待批计划 |
| Deny | 不接受效果，不提供审批入口 | 不接受当前命令效果 |

NeedApproval 回应在原判断字段之外返回 `check_receipt`：

```json
{
  "kind": "check",
  "payload": {
    "decision": "need_approval",
    "reasons": ["..."],
    "decision_trace": {},
    "check_receipt": {
      "check_id": {"session_id": "example-session", "sequence_no": 7},
      "state_revision": 9
    }
  }
}
```

上例为省略详细追踪字段的结构示意，实际回应使用完整 CheckResponse。可信控制器使用原回执发送授权，不重新提交命令：

```json
{
  "kind": "authorize",
  "payload": {
    "check_id": {"session_id": "example-session", "sequence_no": 7},
    "state_revision": 9,
    "approved": true,
    "authority": "simulated_user"
  }
}
```

`approved: false` 表示拒绝；`authority` 可为 `user`、`host`、`simulated_user`。该字段记录来源，不是身份认证凭据；提交通道必须由可信 Harness 或实验控制器掌握，不能把模型输出或工具 stdout 当授权。

审批引用保存的完整请求、原候选变更和原政策。会话状态或政策改变后，原计划失效；审批不能改写原 NeedApproval 判断，也不能覆盖 Deny。获批只表示接受推定效果，不表示 Bash 实际执行成功。

重复的相同授权返回已记录回应，不重复应用；同一检查的冲突授权被拒绝。保留最近 256 个授权重试回执，更早的 ID 过期后报错，不会再次应用。待批计划和授权记录随快照和事件流恢复。

## 能力协商和客户端

`ping` 回应的 `approval_protocol: 1` 同时声明单次审批与仅判断支持。旧回应没有此字段，新控制器必须拒绝降级，不能试发 `judge_only` 给旧服务。

Rust 客户端新增 `check_with_receipt_unix_socket` 和 `authorize_unix_socket`。前者先验证能力再检查。旧 `check_unix_socket` 保留原默认调用方式，但传入仅判断意图时也必须先验证能力。stdio 控制器应先发 ping 并核对协议，再发送 check 或 authorize。

独立持久 Shell 应使用独立 session ID。本阶段没有跨 Shell 状态流的共享绑定协议。Claude、Codex 和 DSH 的现有适配器仍保留原宿主行为，未把 PostToolUse、退出码或出现执行结果追认为用户审批；自动关联宿主批准事件尚未接入。

## 持久化失败

有 store 的运行时在事件写入并同步日志后才返回接受成功，SQLite 物化和检查点仍异步完成。待批检查和授权分别落盘，恢复不需要重新推理。

内存分析先于日志确认。若写入或确认失败，该运行时停止接受后续请求，不返回成功；当前请求可能已经部分写入，必须从持久日志核对，不能自动重发未知工作。此阶段采用失败后停止的保护，不声称内存和磁盘已实现可回滚的事务提交。

## 历史候选和预算保护

`StateCandidate` 是 Graph 中的类型化事实，记录对象、作用域、候选值、序号和源位置。对象索引只保存节点引用，可从 Graph 重建，不单独持久化。候选替代关系不伪装成普通内容传播边；Summary 仍表示最新推定状态，不是安全历史的唯一来源。

现有有序重放在变量赋值、unset、alias、函数定义和位置参数变化时输出候选事实，保留同一输入中的中间值。已调用函数的中间全局写入可回传，普通局部变量和函数位置参数不回传到持久 Shell。当前命令候选和普通效果一起暂存：Allow 或单次批准才提交，未批准、拒绝、Deny 和仅判断都不提交这些当前命令效果。是否跨请求保留还受原有 Shell 持久能力约束。

查询限定对象类型、作用域、序号和源位置，分别报告候选与不完整状态。缺失引用、超限和未知值不能被解释为“已证明无风险”。旧的独立 `SafetyHistory` 类型不参与当前决策，也不作为第二本权威账本。

`analysis.budgets` 提供以下默认上限；零表示没有容量，不表示无限：

| 项目 | 默认上限 |
| --- | ---: |
| Graph 节点 | 100000 |
| Graph 边 | 300000 |
| 状态对象 | 16384 |
| 单对象不同候选 | 256 |
| 单候选值和对象标识的字节限额 | 65536 |
| 候选历史载荷总预算 | 67108864 |
| 单请求命令字节 | 1048576 |

候选记录和查询还受有界工作量限制。以上是分析结构和载荷限额，不是进程堆内存的精确上限，也不是性能调优结论。

达到容量或搜索不完整时，Graph 保存不可自动清除的 `AnalysisIncomplete` 事实，后续判断至少 Ask，原有硬 Deny 保留。`Observe` 配置、单次批准、提高限额、重启或日志压缩都不能清除该状态。当前实现采用整个会话的保守模式：冻结后不继续扩充推定效果图，新的原始检查与批准仍写入审计日志。真实持久化失败则停止服务并报错，不以 Ask 冒充已保存成功。

## 后续实现范围

仍需把历史候选接入现有风险消费者，并贯通同一 action 内候选传播、完整快照观察、工作目录、路径和文件来源，定义旧快照的历史覆盖范围，以及宿主审批关联。特别是“候选已经保存”不等于“后续使用已经逐候选判定”。只有完成这些路径及相应回归后，才能宣称安全覆盖、unset 或清理不会解除风险。原始结果、冻结输入、旧监控和已安装程序均不由本分支修改。
